## 1. Ce qu'il fait

**Identité** : dépôt officiel `deepseek-ai/deepseek-harness` (description « Everything is a Plugin », créé le 13/08/2026, dernier push 17/10/2026, TypeScript, ~258 000 étoiles). Paquet npm `@deepseek-ai/dsh`, dernière version `0.2.1-rc.2` (36 versions, licence MIT aussi côté npm). **« Developer preview » : le README annonce des ruptures de compatibilité**, et `SAFETY.md` dit qu'il n'a subi aucun audit de sécurité.

**Principe** : un harnais d'agent (équivalent de Claude Code : boucle modèle ↔ outils, sessions, interface web `npx @deepseek-ai/dsh web`, application bureau, mode sans interface, SDK TypeScript et Python). Tout est un *plugin* du cadre Cordis : un service (« définition »), des fournisseurs qui l'implémentent, des consommateurs (outils, commandes). Un « profil » (`cordis.patch.yml`) liste les plugins montés ; `headless`, `web-app`, `sdk-app`, `acp-app`, `base` sont des profils.

**Les pièces utiles pour nous**
- **Compétences (skills)** : registre à fournisseurs (`ctx.skills`). Le fournisseur « fichiers » lit `.dsh/skills`, `.agents/skills`, des dossiers à soi, `~/.dsh/skills`, `~/.agents/skills`. Le modèle reçoit un catalogue `nom + description` (≤ 500 caractères, texte échappé), recharge le corps à la demande par l'outil `skill`, et le catalogue est remplacé en entier quand son empreinte change. Le corps est relu à chaque chargement (aucun cache à invalider). Un watcher rafraîchit le catalogue quand on ajoute ou renomme une skill.
- **Sous-agents** : l'outil `subagent` démarre un enfant et rend tout de suite un identifiant ; la fin arrive plus tard sous forme d'avis. Fournisseurs : `spawn` (enfant neuf), `fork` (enfant qui reprend l'historique du parent), et hors processus : ACP, **Codex, Claude Code (via le SDK officiel)**, un autre dsh. Options : préréglage d'agent propre à l'enfant (`allowedAgentPresets`), profondeur maximale (`maxDepth`, 1 par défaut), **schéma de sortie JSON validé** (`outputSchema`), modèle et effort propres. Messages entre agents voisins (`send_message`), interruption, liste.
- **Scripts d'orchestration (`workflow`)** : le modèle écrit un script JS (`agent()`, `parallel()`, `pipeline()`, `phase()`, `log()`), exécuté dans un processus à part ; un enfant qui échoue rend `null` (le script décide), une faute d'usage de l'API tue le script bruyamment ; plafond du nombre total d'enfants. **`ralph`** (expérimental) : boucle de tours d'enfants neufs sur un objectif fixe, où seul un rapport structuré borné passe d'un tour à l'autre (`continue` / `complete` / `blocked` + preuves + prochaines étapes ; rapport invalide = échec, pas de troncature) ; l'espace de travail sert de mémoire.
- **Contexte** : compaction automatique quand `W × 0,8` ou `W − sortie − 65 536` est atteint (le plus petit), en gardant verbatim les 16 % les plus récents, avec **un seul appel de modèle de plus** pour le résumé ; relance après erreur « contexte dépassé » ; politique par modèle ; verrou écrit dans le journal (un verrou orphelin est détecté après un plantage). **Élagueur de résultats d'outils** : au-delà de 8 192 caractères, on garde 4 096 de tête + marqueur + 1 024 de queue, l'original reste dans le journal. **Spill** : un résultat trop gros (`maxInlineTokens` 12 500) est écrit dans un fichier, le modèle reçoit un aperçu + le chemin. **Rappel de répétition** : au 3ᵉ, 5ᵉ, 8ᵉ appel identique de suite, un message demande de changer d'approche (conseil, jamais un blocage ; remis à zéro par un message de l'utilisateur). **Délai par appel d'outil** (`timeout-policy`).
- **Droits** : (a) le *sandbox* confine les processus (`read-only` / `workspace-write` / `danger-full-access` ; Linux bwrap/Landlock, macOS Seatbelt, **Windows jeton restreint + ACL**) ; (b) l'*approbation* est binaire par session : `ask` (un humain répond, sinon refus) ou `never` (tout refusé, pour CI) ; (c) des *préréglages* nommés regroupent les deux ; (d) le tuyau d'exécution d'un outil est : `tools/pre-execute` (autoriser / refuser / demander, programmable) → *gardes monotones* (peuvent seulement refuser, jamais ré-autoriser) → exécution → `post-execute` (bloquer / remplacer le résultat) ; (e) `ToolRestriction` : liste blanche / noire **par nom d'outil**, héritée par portée (un enfant peut en recevoir une plus étroite que le parent).
- **Mode sans interface** : `dsh --profile headless "tâche"` (ou la tâche sur stdin). Rien n'écoute sur un port. Sortie texte, ou **`--json` = événements ligne à ligne** (`session`, `status`, `text`, `thinking`, `tool_call`, `tool_result`, `final`). Code de sortie 0 = fini, 1 = abandon ou erreur. `--session-id` reprend la conversation, avec refus si le dossier de travail, le préréglage ou la nature de la session ne correspondent pas. Les clés viennent de l'environnement puis du `.env`, pas du coffre de l'interface.
- **Plusieurs fournisseurs de modèles** : DeepSeek officiel (`deepseek-flash`, texte + images, et `deepseek-v4-pro`, texte seul, 1 000 000 de jetons de contexte chacun) ; un catalogue via pi-ai (`anthropic`, `openai`, `moonshotai`, `zai`…) ; des API maison selon trois protocoles (OpenAI Chat, OpenAI Responses, Anthropic Messages). Relances automatiques côté fournisseur (5 par défaut). Changer de modèle ne demande pas de redémarrer.
- **Reprise et points d'arrêt humains** : journal de session en JSONL compressé, ajout seulement, un seul écrivain par session, reprise par identifiant ; mode *plan* (`/plan`, l'outil `exit_plan_mode` présente le plan à l'humain, qui approuve ou renvoie planifier ; il *guide* sans restreindre) ; *goal* (un objectif durable par session : actif / en pause / bloqué avec code de raison / terminé, plafond de tours, modifications par comparaison de révision) ; outil `ask_user` ; planificateur (`schedule`) dont nous ne voulons pas.

## 3. Ce qui ne nous sert pas

- **L'architecture Cordis / « tout est plugin »** : élégante, mais lourde (≈ 11 500 fichiers hors traductions, ~350 notes de conception). Nous avons ~1 000 lignes d'orchestration lisibles ; remplacer des fichiers de rôle par des plugins ne rend pas l'équipe plus intelligente. Copier ce cadre serait un projet à lui seul, pour un gain nul sur les vidéos.
- **Son interface** (web, bureau, ACP, éditeur de cartes, marché de plugins) : nous avons déjà la nôtre, taillée pour Noam.
- **Les droits par fichier** : dsh filtre par *nom d'outil* (`ToolRestriction`) et décide d'autoriser/refuser/demander via une fonction `pre-execute` qu'il faut écrire ; il n'y a pas, dans ce que j'ai lu, d'équivalent natif de notre `Edit(fichier)` / `Write(fichier)` fichier par fichier. **Sur ce point, Claude Code est plus fin que dsh** (à confirmer dans le code : je n'ai lu que les docs). Le sandbox de dsh confine les *processus* au dossier de travail, ce qui est autre chose.
- **Approbation binaire `ask` / `never`** : plus pauvre que nos permissions par motif de commande.
- **Planificateur, goal, jobs, agent-team (expérimental), mods Claude Code, ralph** : `schedule` est exclu par décision de Noam (« rien d'automatique ») ; goal/ralph rejouent ce que `equipe.mjs` fait déjà en plus fixe ; agent-team (tâches partagées, boîte aux lettres) est expérimental et répond à un besoin que nous n'avons pas (les sections sont indépendantes par construction).
- **Mémoire de session en JSONL compressé, format versionné (v0 → v4)** : nous avons git et `constructions.json`.
- **Skills Office de dsh** (`skill-office`) : Word/PowerPoint/Excel, hors sujet.
- **Modèles gratuits ou bon marché comme gain d'« intelligence »** : le harnais n'ajoute pas de qualité au modèle. Rien dans la doc ne mesure la qualité d'un modèle DeepSeek sur du Three.js motion design ; `BENCHMARK.md` n'a pas été lu.

**Ce qui est mieux chez eux, franchement** : (1) le contrôle de tout ce qui entre dans le contexte est une fonction du harnais (élagueur, spill, compaction réglable, rappel de répétition) alors que chez nous on le compense à la main dans les consignes ; (2) le bilan de fin structuré avec état « bloqué » ; (3) le sandbox Windows ; (4) le mode `--json` et la reprise vérifiée sont soignés ; (5) plusieurs fournisseurs de modèles sans bricolage. **Ce qui n'est pas mieux** : les droits fichier par fichier (voir plus haut), la maturité (aperçu de développeur, non audité, ruptures annoncées), et la simplicité : notre `equipe.mjs` + `roles/*.md` se lit en dix minutes.

## 5. Recommandation

**Garder Claude Code comme moteur de l'équipe et prendre des idées de dsh.** Ordre conseillé (quatre petits changements, aucun risque pour le rendu) :
1. **Bilan structuré de fin d'agent** avec état `blocked` (idée 1) : c'est le seul vrai trou de fiabilité repéré.
2. **Paquets plus petits** : règles du style filtrées par plage ou déportées dans `references/` (idée 5).
3. **Plafonds durs et garde de répétition** (idées 14 et 3) : protège le coût.
4. **Contrôle des en-têtes de skills** dans `lib/skills.mjs` (idée 6).

**Faire tourner certains rôles par dsh en mode Éco : pas maintenant.** Pour un essai plus tard, un seul rôle à faible enjeu : le chercheur d'images (famille « vérifier », aujourd'hui Haiku), ou les passes mécaniques déjà confiées à DeepSeek par `opencode`. Risques, tous réels :
- **Maturité** : aperçu de développeur, ruptures annoncées (nous avons déjà payé des pièges de ce genre), non audité. Chaque mise à jour peut casser un rôle.
- **Droits plus grossiers** : pas de `Edit(fichier)` natif. Il faudrait écrire un plugin `pre-execute` qui refuse tout fichier hors de celui du rôle, et le tester ; en attendant, un agent dsh pourrait écrire dans les fichiers d'un autre.
- **Windows** : le sandbox à jeton restreint est récent (décision d'août 2026) ; il n'a pas été essayé ici.
- **Qualité** : aucune preuve que les modèles DeepSeek tiennent la qualité des constructeurs (Three.js, caméra, vérification d'images). Nos 21 défauts plantés (`outils/test-check.mjs`) et le détecteur d'à-coups feraient un banc d'essai honnête : à utiliser avant tout changement de rôle.
- **Données** : le contenu des projets (scripts, images de référence) partirait vers l'API DeepSeek. Aucune donnée perso ne doit y figurer (règle de CLAUDE.md) ; la clé doit rester en variable d'environnement (le profil `headless` de dsh lit l'environnement, ce qui va dans le bon sens ; les profils web enregistrent la clé dans `~/.dsh/.credentials.yaml`, à éviter).
- **Mélanger les moteurs** : dsh sait lancer Claude Code comme enfant (`subagent-claude-code`) ; cela n'apporte rien pour nous et la question de l'usage de l'abonnement de Noam par un harnais tiers reste ouverte (**à vérifier avant tout essai**).

**Réponse à la question de Noam** : le logiciel ne deviendra pas plus fluide ni plus intelligent en changeant de harnais ; il gagnera en prenant quelques *garde-fous* qu'eux ont bien faits (bilan structuré, contexte plus petit, plafonds). Les modèles bon marché restent pour le travail mécanique.
